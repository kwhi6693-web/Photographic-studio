# Photographic Studio App 方案设计

2026-11-13 · 草案 v0.1

> 基于仓库 main（v1.0.4）与 PR #7（v1.0.5）的现状。所有耗时和成本都是估计，第 1 阶段原型实测后更新。

## 1. 目标与范围

**定位**：给喜欢拍照、不想花时间后期的人。选图 → 等一会儿 → 拿到一张「明显更好、仍是原片、没有 AI 味」的成片。

**用户只做三件事**：选照片、等、保存。没有滑杆、滤镜、版本选择。

**成功标准（上线前必须达到）**

| 项目 | 标准 |
|---|---|
| 质量 | 竞品盲比（苹果照片自动增强、Lightroom 自动）中，用户选本产品的比例明显更高 |
| 速度 | 单张从上传完成到出片 ≤ 60 秒（p90） |
| 稳定 | 成功率 ≥ 98%；失败时自动退回 N 直出，不让用户空手 |
| 一致 | 同一张照片处理两次，用户看不出差别 |
| 成本 | 单张成本低于定价可承受的上限（第 7 节） |

**不做**：人像、视频、滤镜风格、手动调参、多版本挑选、社交分享社区。

## 2. 总体架构

```
iPhone App (SwiftUI)
  │  上传原图（HTTPS，直传对象存储）/ 轮询或推送结果
  ▼
API 服务（无状态）── 账号、订阅校验、配额、限流
  │  写入任务
  ▼
任务队列 ──► Worker（Python，复用现有工具）
               ├─ 调用视觉模型：读片 + 导演单 + 验收
               ├─ 调用图像生成 API：G（光与色方向）
               └─ 确定性工具：look_transfer → grade → 检查 → settle → reframe → n_trim
  ▼
对象存储（原图 / 成片，限时保存后自动删除）
```

**分工原则**：流程顺序由代码决定；AI 只在三处做判断（读片、写导演单、验收）；所有像素操作都由确定性工具完成。这是从「GPT 读 SKILL.md 自己执行」改成「代码编排」的核心变化，也是速度、稳定、一致性的来源。

## 3. 处理流水线

| 步骤 | 执行者 | 输入 → 输出 | 现有对应 | 预计耗时 |
|---|---|---|---|---|
| 1 预处理 | 代码 | 原图 → 工作图（长边 1536）、EXIF、HEIC 解码 | 新增 | 1 s |
| 2 测量 | 代码 | 工作图 → 测量数据 | measure.py | 1 s |
| 3 读片 + 导演单 | 视觉模型（一次调用，结构化 JSON 输出） | 工作图 + 测量 → 题材、主角、导演单、G 提示词、N 参数 | SKILL 第 3–4 步 | 5–10 s |
| 4 拒绝判断 | 代码 + 第 3 步结果 | 人像 → 返回「不支持」 | SKILL「拿不到成片」 | 0 s |
| 5 G | 图像生成 API | 原图 + 提示词 → G 稿 | 第 5 步 | 15–30 s（最大不确定项） |
| 6 G 场景检查 | 代码 | 原图 + G → 通过 / 作废 | check_g_output.py | 1 s |
| 7 出片 | 代码 | 原图 + G + 参数 → 成片 | finish.py | 10–30 s |
| 8 力度校准 | 代码 | → 校准后成片 | settle.py | 10–30 s |
| 9 验收 | 视觉模型（可选，一次调用） | 原图 + 成片 + 导演单 → 交付 / 补一轮 | 第 6 步 | 5 s |
| 10 构图与收尾 | 代码 | → 最终成片 | reframe.py、n_trim.py | 2 s |
| 11 全尺寸输出 | 代码 | 把调色结果应用到原分辨率 | 新增 | 3–5 s |

**合计约 50–110 秒**，要压到 60 秒以内，优先做：

- 第 5 步与第 2 步并行，第 3 步完成后立即发 G 请求；
- finish.py 的路线阶梯在多核上并行跑，取第一个合格的；
- settle.py 的二分搜索改为在缩小图上搜参数，最后只在全尺寸上应用一次；
- 第 9 步默认关闭，只在检查报出问题时调用。

**失败兜底**：G 超时或作废 → 直接走 N 直出（finish 的已有路线），仍然交付；任何工具报错 → 交付已经完成的最后一版，并在后台记录。

**第 11 步是新难点**：现有工具在 1152–1536 像素上跑。手机原图 12–48MP，直接全尺寸跑太慢。做法是在工作图上算出调色和光色映射，再以「低分辨率映射 + 原图细节」的方式应用到全尺寸，保证细节全部来自原图。需要单独验证。

## 4. AI 服务选型

**视觉模型（读片 / 导演单 / 验收）**：要求能看图、能按 JSON 模式输出、单次 < 10 秒。候选为主流多模态模型 API。验证方法：用测试集里已认可的照片，比较新模型写出的导演单跑出的成片与现有成片，盲比不差即可。

**图像生成（G）**：这是整个方案最大的风险。要求：

1. 能以原图为输入做编辑（不是从零生成）；
2. 构图不变，能通过 check_g_output.py 的场景检查；
3. 单次 ≤ 30 秒，价格可接受；
4. 允许商用。

**验证方法（第 1 阶段第一件事）**：拿测试集里 21 张真实批次原图（tests/fixtures/real_g），各用候选 API 生成 G，走完整流水线，和当时 ChatGPT 的成片盲比。只要有一个候选能做到「不差」，方案就成立；都做不到，就要考虑退回纯 N（无 G）版本，并重新评估产品卖点。

**中国区**：境外模型 API 在中国区不能直接用于上线服务，需要境内可备案的模型；先做海外区。

## 5. 后端设计

- **API**：`POST /jobs`（返回上传地址）、`GET /jobs/{id}`（状态、结果地址）、`DELETE /jobs/{id}`、`DELETE /account`。
- **上传**：App 直接把原图上传到对象存储的预签名地址，API 服务不经手大文件。
- **队列与 Worker**：任务队列 + 可自动扩容的 Worker 容器；每个 Worker 单张处理，失败自动重试一次。
- **存储与删除**：原图和成片默认 7 天后自动删除；用户可随时删除；不用于训练。
- **限流与防滥用**：按账号和设备限频；单张文件大小上限；订阅状态由服务端向苹果校验。
- **监控**：每一步耗时、成功率、G 作废率、退回 N 直出的比例、单张成本，并设置异常报警。
- **回执**：每张保留一份 receipt（与现在的格式一致），用于排查和质量统计，随照片一起到期删除。

## 6. iOS App 设计

**技术栈**：SwiftUI；PhotosPicker 选图；后台上传（URLSession background）；StoreKit 2 订阅；APNs 推送完成通知。

**页面流程**

1. **首页**：一个大按钮「选照片」，下面是最近的成片。
2. **选图**：可多选（单次上限，例如 20 张）。
3. **处理中**：每张一个进度卡片；可以离开 App，完成后推送。
4. **结果**：成片全屏显示；按住看原图；一键「存到相册」或「全部保存」。不显示参数和检查结论。
5. **设置**：订阅、删除我的照片、删除账号、隐私说明。

**关键体验**：

- 首次使用三屏引导：能修什么（风景、建筑、夜景、室内、静物），不修什么（人像）；
- 失败时用一句话说明原因，例如「这张是人像，暂不支持」；
- 保存回相册时保留原图的拍摄时间和地点，用户可在设置里关掉地点。

## 7. 账号、付费与成本模型

**账号**：Sign in with Apple；App 内可删除账号。

**付费**（通过苹果内购）：

- 免费试用：例如 10 张；
- 订阅：按月，每月包含一定张数；超出部分可单独购买张数包。

**单张成本构成**（第 1 阶段实测后填写）：

| 项目 | 估计 |
|---|---|
| 视觉模型 1–2 次 | 待测 |
| 图像生成 1 次（偶尔 2 次） | 待测，通常是最大的一项 |
| 计算（约 1 分钟 CPU） | 待测 |
| 存储与流量 | 很小 |

定价原则：订阅价 ×（1 − 苹果分成）÷ 月均张数 ≥ 单张成本的 3 倍。

## 8. 隐私、合规与许可证

- **隐私政策与 App Store 隐私标签**：照片会上传到服务器处理、保存期限、是否发送给第三方 AI 服务（需写明）。
- **不用于训练**：写进隐私政策，并选用承诺不训练的 API 条款。
- **AI 处理标注**：在成片的元数据中注明经过 AI 辅助处理；长期考虑 C2PA 内容凭证，作为「像素来自原片」的证明（卖点之一）。
- **许可证**：仓库现为 AGPL-3.0，与 App Store 条款普遍被认为有冲突。代码由项目所有者拥有，上架前改为适合闭源分发的许可（或双许可）。需专业人士确认。
- **依赖**：numpy（BSD）、Pillow（MIT-CMU）、OpenCV（Apache 2.0）可商用。
- **中国区**：ICP 备案、生成式 AI 服务备案和算法登记，需境内模型；单独立项。

## 9. 质量保障

- **离线测试集**：现有 tests/fixtures 扩到 200+ 张，覆盖各题材和光线；每次发版跑完整流水线。
- **回归**：认可过的成片作为金标准，新版本不得变差（沿用现在的逐像素 / 统计回归）。
- **盲比**：每个影响成片的改动都做盲比（沿用现在的验收方式）。
- **线上信号**：用户「没保存就离开」「重新处理」「点了不满意」的比例；每周抽样人工查看。
- **用户反馈**：结果页一个「这张不好」按钮，附原因选项，进入下一轮测试集。

## 10. 里程碑、验收门槛与风险

| 阶段 | 内容 | 时长（兼职估计） | 通过门槛 |
|---|---|---|---|
| 0 | 稳定现有 skill；竞品盲比 | 2–3 周 | 稳定标准达到；竞品盲比胜出 |
| 1 | 服务器原型：代码编排 + G 的 API 验证 + 全尺寸输出 | 3–4 周 | ≤ 60 秒；单张成本可接受；盲比不差于现在 |
| 2 | 后端产品化 | 3–4 周 | 并发几十人稳定 |
| 3 | iOS App MVP | 4–6 周 | 自用一周无大问题 |
| 4 | 合规与 TestFlight 内测（10–20 人） | 2–3 周 | 内测基本满意，无严重 bug |
| 5 | 上架审核 | 1–2 周 | 上架（先海外区） |

**主要风险与对策**

| 风险 | 影响 | 对策 |
|---|---|---|
| G 的 API 效果不如 ChatGPT | 卖点不成立 | 第 1 阶段最先验证；不行就评估纯 N 版本 |
| 速度达不到 60 秒 | 体验差 | 并行、缩小图搜参数、默认关闭验收调用 |
| 单张成本过高 | 定价没有竞争力 | 只在需要时调用 G；分档订阅 |
| 竞品盲比不胜出 | 没有付费理由 | 阶段 0 就验证，不胜出不进入后续阶段 |
| 全尺寸输出损失细节 | 质量下降 | 低分辨率映射 + 原图细节，单独测试 |
| 许可证与区域合规 | 无法上架 | 提前定许可证；先海外区 |

**下一步**：阶段 0 的竞品盲比，现在就能做，不需要额度。
